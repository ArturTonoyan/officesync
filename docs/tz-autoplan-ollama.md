# ТЗ: автопланирование офиса (алгоритм + Ollama)

**Проект:** OfficeSync  
**Модуль:** Конструктор планов этажа (`/constructor`)  
**Версия:** 1.0 (без ML-ранкера)  
**Стек:** React + JBay Floorplan, NestJS, Ollama (локальная LLM)

---

## 1. Цель

Дать пользователю возможность:

1. Зафиксировать неизменяемую оболочку этажа (стены, окна, двери и т.д.).
2. Описать текстом и формой, как обустроить офис.
3. Получить вариант(ы) расстановки мебели и зон от **алгоритма**.
4. Править план текстом через **Ollama** и руками в редакторе.
5. В реальном времени видеть **красные подсветки**, если нарушены нормы (rule engine, не нейросеть).

**Вне скоупа v1:** обучение нейросети, ранжирование вариантов ML, онлайн-дообучение на правках.

---

## 2. Роли

| Роль | Доступ |
|------|--------|
| ADMIN | Полный доступ: оболочка, автоплан, текстовые правки, сохранение |
| Прочие роли | Только просмотр 2D/3D (как сейчас `noedit`), без автоплана |

---

## 3. Пользовательский сценарий (happy path)

### Шаг 1. Оболочка этажа

Пользователь в режиме **Редактор** рисует или уточняет то, что алгоритм **не двигает**:

- стены, комнаты (полигоны);
- окна, двери, проёмы;
- санузлы / мокрые зоны (если отмечены типом комнаты или объектом);
- розетки, щиты, колонны, огнетушители (если есть в каталоге) — как **фиксированные** объекты.

**Критерий готовности оболочки:** есть хотя бы одна комната с площадью > 0 и хотя бы один вход (дверь/проём) *или* явное подтверждение «продолжить без двери» с предупреждением.

### Шаг 2. Запуск автоплана

Кнопка в верхней панели конструктора: **«Автоплан»**.

Открывается боковая панель / модальное окно **«Параметры обустройства»**.

### Шаг 3. Ввод требований

Пользователь заполняет блоки (все опциональны, кроме минимума — см. §5):

#### 3.1. Источник данных

- [ ] Подтянуть с этажа из БД: сотрудники, оборудование, привязки.
- [ ] Использовать только ручной ввод / каталог.

При «Подтянуть из БД» система показывает сводку:

- число сотрудников на этаже;
- список оборудования (тип, кол-во);
- уже существующие маркеры рабочих мест (если есть).

Пользователь может снять галочки с отдельных позиций («не учитывать монитор X»).

#### 3.2. Зоны и комнаты (форма)

| Поле | Тип | Пример |
|------|-----|--------|
| Число рабочих мест | number | 24 |
| Переговорные (бронируемые) | number | 2 |
| Конференц-зал | number (0/1) | 1 |
| Кабинеты с привязкой к пользователю | список userId + метка | «Иванов — кабинет» |
| Зона отдыха / lounge | boolean / number | да |
| Кухня / пантри | boolean | да |
| Ресепшен | boolean | нет |

#### 3.3. Мебель и оборудование

- Выбор из каталога конструктора (чекбоксы / лимиты «макс. N»).
- Опция **«Разрешить дополнительную мебель»** (алгоритм может добавить растения, диваны и т.п. сверх БД).
- Опция **«Только объекты из БД + выбранный каталог»** (строгий режим).

#### 3.4. Стиль и предпочтения (слайдеры / теги)

- Плотность рассадки: низкая / средняя / высокая.
- Больше растений.
- Больше зон отдыха.
- Больше тихих зон / фокус-будок.
- Приоритет света у рабочих мест (у окон), если окна есть на плане.

#### 3.5. Текстовое ТЗ (свободный ввод)

Многострочное поле, например:

> Минимум 2 переговорки с броню. Конференц на 12 человек у окна.
> Кабинет для Иванова у северной стены. Остальное — open space.
> Можно добавить растения и диваны у ресепшена.

Текст обрабатывает **Ollama** → структурированный JSON требований (см. §7).

Кнопка **«Распознать текст»** (опционально до генерации) показывает пользователю распознанные пункты для подтверждения/правки.

### Шаг 4. Генерация

Кнопка **«Создать план»**.

Индикатор прогресса: «Разбор требований → расстановка → проверка норм».

Результат:

- на canvas применяется новый набор мебели/зон (оболочка не меняется);
- справа — краткий отчёт:
  - **Запрошено → Размещено** (числа по местам, переговоркам, конференц, кабинетам, lounge, ресепшен, пантри);
  - что сделано (текстовые строки);
  - что не удалось (например, «конференц не влез по площади»);
  - **Оборудование (БД)**: сколько выбрано в превью, сколько уже в комплектациях столов, сколько свободно; пометка, что автоплан **не** раскладывает оборудование на столы;
  - список сработавших норм (ok / warn).

Если вариантов несколько (v1 — достаточно **1**, желательно до **3** с переключением «Вариант A/B/C»).

Действия:

- **Применить** (уже на плане) / **Отменить** (откат к состоянию до автоплана);
- **Сохранить этаж** — штатное сохранение `planData` (`plan` + `markers` + `workplaceKits`).

### Шаг 4.1. Комплектация рабочего места (ручная)

После расстановки столов пользователь в режиме редактора:

1. Выделяет стол (desk) на плане.
2. Открывается панель **«Комплектация рабочего места»**.
3. Добавляет на стол реальные единицы из БД (`equipments`: ПК, монитор, клавиатура, мышь и т.д.) — каждая единица может быть только на одном столе этажа.
4. Двигает слоты относительно центра стола (смещения ox/oy); символы синхронизируются при перемещении стола.
5. **Копировать рабочее место** — дублирует стол и шаблон раскладки; к слотам заново привязываются **свободные** единицы того же типа из БД; если свободных нет — слот без инвентаря + предупреждение.

Данные kits хранятся в `planData.workplaceKits`. Авторасстановка оборудования алгоритмом автоплана — вне скоупа этой итерации.

### Шаг 5. Текстовые правки (Ollama)

Панель **«Правка текстом»** (чат в конструкторе):

Примеры:

- «Сдвинь переговорки ближе к входу»;
- «Добавь ещё 4 стола»;
- «Убери растения у выхода»;
- «Сделай кабинет Иванова больше».

Поток:

1. Ollama → JSON-команда(ы) правки.
2. Алгоритм применяет патч **или** частичный пересчёт зоны.
3. Пользователь видит diff на плане + краткое текстовое подтверждение («Добавлено 4 стола в open space»).

Если команда неоднозначна — Ollama/UI задаёт уточняющий вопрос, план не меняется.

### Шаг 6. Ручные правки + нормоконтроль

Пользователь двигает объекты мышкой как сейчас.

После каждого изменения (debounce ~300 ms) **rule engine**:

- подсвечивает нарушающие объекты/зоны **красным**;
- в панели «Нормы» — список нарушений с кратким текстом (без обязательного вызова Ollama);
- опционально кнопка **«Объяснить»** → Ollama формулирует понятное объяснение по списку нарушений.

---

## 4. Что алгоритм меняет / не меняет

| Можно менять | Нельзя менять (фиксировано) |
|--------------|-----------------------------|
| Мебель, перегородки open space (если разрешены), маркеры мест | Стены здания / несущий контур |
| Рассадка столов, стульев, шкафов | Окна, двери, проёмы |
| Зоны переговорок (логические комнаты/мебель) | Санузел, мокрые зоны |
| Растения, lounge, доп. объекты каталога | Розетки, щиты, колонны, пожарное оборудование |
| Признаки «бронируемо», привязка user к кабинету | Масштаб и единица плана |

При конфликте «пользователь просит снести стену» — отказ + сообщение, стена не трогается.

---

## 5. Минимальные входные данные для генерации

Обязательно хотя бы одно из:

- число рабочих мест > 0, **или**
- подтяжка из БД с N сотрудниками / местами > 0, **или**
- непустой текст, из которого Ollama извлекает `workstations` / зоны.

Иначе — ошибка валидации формы: «Укажите число мест, подтяните данные с этажа или опишите задачу текстом».

## 6. Нормы v1 (rule engine, красная подсветка)

Конкретные числа выносятся в конфиг `rules.json` (для диплома — со ссылками на СП/СанПиН в пояснительной записке).

Минимальный набор проверок v1:

1. Нет пересечений мебели друг с другом и со стенами.
2. Минимальная ширина основного прохода.
3. Зона открывания двери свободна.
4. Упрощённый путь от рабочего места до ближайшего выхода ≤ лимита (по сетке/графу).
5. Минимальная площадь на рабочее место (плотность).
6. Не заставлять фиксированные объекты (щит, огнетушитель, розетки — clearance).

Статусы нарушения: `error` (красный), `warning` (оранжевый, мягкие рекомендации).

## 7. Контракт: текст → JSON (Ollama)

Ollama **не рисует** координаты мебели. Только структурирует intent.

Пример выхода:

```json
{
  "workstations": 24,
  "meetingRooms": { "count": 2, "bookable": true, "minSeats": 4 },
  "conferenceRoom": { "count": 1, "minSeats": 12, "preferNearWindow": true },
  "privateOffices": [
    { "userId": "…", "label": "Иванов", "prefer": "north_wall" }
  ],
  "amenities": {
    "lounge": true,
    "plants": "more",
    "pantry": true,
    "reception": false
  },
  "density": "medium",
  "allowExtraFurniture": true,
  "notes": ["open space для остальных"]
}
```

Невалидный JSON / пустой разбор → ошибка пользователю: «Не удалось разобрать требования, уточните формулировку» + возможность править форму вручную.

Для текстовых правок — отдельная схема команд, например:

```json
{
  "actions": [
    { "type": "add_workstations", "count": 4 },
    { "type": "move_zone", "zone": "meeting", "toward": "entrance" },
    { "type": "remove_category", "category": "plants", "near": "exit" }
  ]
}
```

Неподдерживаемое действие → отказ с пояснением, без порчи плана.

## 8. UI — элементы интерфейса

| Элемент | Где |
|---------|-----|
| Кнопка «Автоплан» | TopMenu конструктора (рядом с Сохранить) |
| Панель параметров | Drawer справа или модалка |
| Поле текста ТЗ + «Распознать» | В панели параметров |
| «Подтянуть из БД» | Чекбокс + превью списка |
| Отчёт генерации | Блок под параметрами / тост + панель |
| Комплектация рабочего места | Панель при выделении стола в редакторе |
| Копировать рабочее место | Кнопка в панели комплектации |
| «Правка текстом» | Вкладка/чат в конструкторе |
| Панель «Нормы» | Список нарушений + клик → фокус на объект |
| Красная/оранжевая подсветка | Overlay на canvas редактора |

Состояния кнопок:

- генерация идёт → disable «Создать» / «Применить правку», показать spinner;
- Ollama недоступна → автоплан по **только форме** (без текста) + баннер «Текстовый разбор временно недоступен».

## 9. Данные и интеграция

### Вход алгоритма

- текущий `FloorPlan` (JBay) + `markers`;
- JSON требований (форма ∪ результат Ollama);
- опционально снимок БД: users / equipment по `floorId`;
- `rules.json`.

### Выход алгоритма

- обновлённый `plan` (furniture / rooms logical) + `markers`;
- `report`: созданные сущности, skipped, violations после генерации;
- не перезаписывать диск, пока пользователь не нажал штатное **Сохранить**.

### Ollama

- переиспользовать инфраструктуру backend (`OLLAMA_BASE_URL`, `OLLAMA_MODEL`), отдельный endpoint под layout (не смешивать с админ-чатом по компании), например:
  - `POST /layout/parse-brief` — текст → JSON требований;
  - `POST /layout/parse-edit` — текст правки → JSON actions;
  - `POST /layout/generate` — plan + requirements → новый plan + report;
  - `POST /layout/validate` — plan → violations (для live-подсветки можно частично на клиенте).

Точные пути API — на усмотрение реализации; в v1 допустим вызов generate через NestJS → Python/`neiroset` или чистый NestJS-модуль.

## 10. Нефункциональные требования

| Требование | Значение |
|------------|----------|
| Время генерации v1 (типовой этаж) | ≤ 10–15 с (цель), ≤ 30 с (допустимо) |
| Live validate | debounce 300 ms, без блокировки UI |
| Отмена | «Отменить автоплан» возвращает snapshot плана |
| Язык UI | русский |
| Логирование | brief JSON, длительность, число нарушений (без ПДн в логах сверх необходимого) |

## 11. Критерии приёмки v1

1. Пользователь рисует оболочку → «Автоплан» → задаёт места формой → получает расстановку без сдвига стен/дверей/окон.
2. Текст «2 бронируемые переговорки» через Ollama попадает в JSON и учитывается алгоритмом (или явный skip в отчёте).
3. «Подтянуть из БД» учитывает сотрудников/оборудование этажа в сводке и генерации.
4. После ручного сужения прохода объект/зона подсвечивается красным, в панели «Нормы» есть пункт нарушения.
5. Текстовая правка «добавь 4 стола» меняет план либо даёт понятный отказ.
6. «Отменить» откатывает автоплан; «Сохранить» пишет `planData` как сейчас.
7. При выключенной Ollama форма без текста всё ещё генерирует план.
8. Отчёт показывает запрошено/размещено и блок оборудования из БД.
9. На выделенном столе можно собрать комплект из БД и скопировать шаблон на новый стол с rebind свободных единиц.

## 13. Вне скоупа v1

- Обучение / дообучение нейросети на правках.
- Полный BIM / точный расчёт по всем СП.
- Автоматический снос/перенос несущих стен.
- Генерация 3D-мебели с нуля.
- Согласование с пожарной инспекцией «в один клик».
- Автоматическая раскладка единиц `equipments` на столы при генерации автоплана.

## 14. Краткая схема для пользователя

```
Оболочка (стены, окна, двери, санузел, розетки…)
        ↓
Автоплан: форма + БД + текст
        ↓
Ollama: текст → JSON требований
        ↓
Алгоритм: расстановка по JSON + нормы
        ↓
План на экране + отчёт (запрошено/размещено, оборудование БД)
        ↓
Комплектация стола из БД / копирование шаблона (по желанию)
        ↓
Правки текстом (Ollama) и/или мышкой
        ↓
Rule engine: красные нарушения в реальном времени
        ↓
Сохранить этаж (plan + markers + workplaceKits)
```
